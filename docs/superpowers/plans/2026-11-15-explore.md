# Explore (players ↔ groups ↔ members ↔ creations) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn Wornby into a connected way to browse public Roblox data: player → their groups → group creations and members → member's full profile → their groups, and so on, with breadcrumbs and working browser Back/Forward. Along the way it builds a **discovered player network** of verified group memberships that answers "which groups do these players share, and why are they connected".

**Architecture:** The Rust backend gets four new read-only, stateless, CDN-cached data feeds (members, experiences, creator assets, user catalog creations). The user catalog feed reuses the existing group-store pipeline by making the creator type a parameter. The frontend keeps its single-page layout. The profile inspector gets a CREATIONS tab. The existing group store modal becomes a tabbed group explorer (STORE / EXPERIENCES / MEMBERS / ASSETS). A breadcrumb trail is saved in `history.state`, so Back/Forward brings it back for free. The network is recorded **as a side effect of data already being loaded**, with no extra Roblox calls and no crawling. It goes into a browser-local IndexedDB graph, the same local-first pattern as the Outfit Archive.

**Tech Stack:** Rust (hyper/reqwest/tokio, Vercel Rust runtime, `rust/*.rs`), React 18 + TS + Tailwind + Radix Tabs + framer-motion, `tsx --test`, Playwright with `page.route` mocks, `cargo test --release`.

**Spec:** the user's approved requirement (2026-11-15), restated:
1. Player profile shows groups, creations, outfits, ARCHIVE.
2. A group opens with info, creations and members.
3. Group members show avatar + username, and every one is clickable.
4. A member opens as a full Wornby profile without losing the navigation context.
5. Keep exploring players → groups → members.
6. Creations for players and groups: clothing/accessories, experiences, other accessible creator assets.
7. Clearly tell apart: made by the player, made by their group, worn/saved.
8. Smooth navigation, no going back to search; preserve context; browser Back/Forward work.
9. Compact and consistent with the current design.
10. (Addition, 2026-11-15) Record discovered public relationships player → group → member; find groups shared by several players; show why two players are connected; let the network grow as people explore; always tell verified group membership apart from friendship. No login, no privacy bypass; keep the read-only, on-demand feeds.
Investigation result (same day, live probes): friend lists are 403 anonymously and are **out of scope**.

## Global Constraints

- No commits, pushes or Production deploys without the user's separate approval. The commit steps below run only after that approval; until then, stop at "tests pass".
- Public data only, anonymous requests only. No Roblox cookie and no Open Cloud key.
- No database. Backend stays stateless. The trail lives only in the browser (`history.state` + `sessionStorage`).
- Existing privacy rule stays: private inventory ⇒ no outfits (live or archived), worn looks only.
- Only `accessFilter=Public` experiences.
- Every creator id passes `parse_id` (u64 > 0). A request without a valid id is answered 400 and never sent upstream, because Roblox catalog search silently returns **unfiltered** results when `CreatorTargetId` is empty.
- Mirror first (`*.roproxy.com`), official host as hedge, via the existing `upstream::get_resilient` / `get_official`.
- Build Rust inside the VS2022 vcvars64 env; build to a scratch target dir if the running app locks `target/`.
- The network is recorded only from responses Wornby already fetched for the person browsing. No background crawling, no prefetching of members or groups to grow the graph.
- Connection copy never says "friend". The only relationship type is `SHARED GROUP`. Its tooltip reads exactly: "Verified Roblox group membership — not a friendship. Roblox keeps friend lists private."
- Labels are uppercase mono like the existing UI ("CREATIONS", "MADE BY", "WORN"). Icons are lucide-react only.

## Rate-limit and performance rules

- Nothing new loads with the profile. Each feed loads only when its tab is opened (lazy), one page at a time, with a "LOAD MORE" button (same style as the store). No automatic loading of every page.
- One thumbnail batch per page (members 50 → 1 headshot call). Thumbnail failures are swallowed, the same as `asset_thumbnails`.
- Server TTL caches (`upstream::Ttl`): members 5 min / 500 entries, experiences 10 min / 500, assets 10 min / 500, keyed `{creatorType}:{id}:{cursor}[:{type}]`.
- CDN: `public, max-age=300, stale-while-revalidate=600` on success. `no-store` on any failure or partial page.
- Every new route is wrapped in `within(STORE_DEADLINE, …)` (13 s; client timeout 15 s).
- Client: `AbortController` per tab fetch, aborted on group/player change. A module-level `Map` page cache keyed by feed+id+cursor makes Back instant and keeps already-loaded pages.
- Per hop cost: member list page = 2 upstream calls; experiences page = 2; assets page = 3; catalog creations = same as a group store page.

## Privacy

- Friends: not shown (Roblox blocks the list anonymously). Nothing in the UI suggests otherwise.
- Members: Roblox makes group member lists public. Wornby shows only what that endpoint returns (username, display name, role, headshot).
- Groups a user is in: existing `groups/roles` behaviour, unchanged.
- Owned inventory: still gated by `can-view-inventory` (unchanged). The new feeds show only *created* items, which Roblox makes public by design.
- Terminated/banned users: the existing profile 404 path shows the existing error. A member who can't be loaded keeps the trail intact.
- No server-side storage of anyone's data. The trail and the network are device-local.
- The network holds only verified public group memberships (user id, name, group id, role, when it was seen and how). A **CLEAR NETWORK** control wipes it.

## Discovered network: local first, shared later?

**Phase 1 (this plan): local only.** An IndexedDB graph in the browser of the person exploring.
- *Nodes:* players `{id, name, displayName, headshotUrl}` and groups `{id, name, iconUrl, memberCount}`.
- *Edges:* `membership {userId, groupId, roleName, roleRank, source: 'profile' | 'members', seenAt}`.
- *Two sources, two levels of trust:*
  - `profile`: a profile load returns the player's **complete** public group list. It replaces that player's previous `profile` edges, so groups the player left disappear.
  - `members`: a member page returns **some** of a group's members. It only adds edges and never deletes.
- *Why connected:* players P and Q are connected when they share a group. The shared groups are `groups(P) ∩ groups(Q)`.
- *Fresh check:* if Q is known only from a member page, Wornby can fetch Q's full group list live with one lightweight call (`/api/users/{id}/groups`, Task 9). That makes the answer complete instead of partial.
- *Size:* capped at 20,000 edges; the oldest `members` edges are pruned first, while `profile` edges are kept.

This needs no backend storage, works offline for what's been seen, and keeps it private. **Limit:** each browser only knows what that browser explored. Nobody benefits from anyone else's exploration.

**Phase 2 (not in this plan; needs your decision): a shared network.** A shared, growing network needs a server database, e.g. Postgres (Neon) or Vercel KV, which you skipped for the archive. Before building it:
- Collecting a cross-user graph of Roblox accounts, many of them minors, is a heavier privacy and Roblox-terms question than showing public data to one viewer.
- It would need: only memberships viewers actually loaded (no crawler), an expiry (e.g. 30 days unless seen again), a removal path for a player, and rate limits on writes.

Phase 1 stores data in a shape that could later be uploaded as-is, so going shared later doesn't mean rebuilding.

## Review Focus

1. A request for creations with id `0`, an id that is too long, or a missing id → 400, and no upstream call is made (prevents the unfiltered-catalog leak). Test: Task 1 `creator_id_validation`.
2. Upstream returns catalog rows from a different creator → those rows are dropped. Test: Task 1 `drops_foreign_creator_rows`.
3. Loop navigation A → G → B → G → A → the trail cuts back to the earlier crumb instead of growing forever, and stays capped at 8. Test: Task 5 `nextTrail` cases.
4. Back after opening a member from a group's MEMBERS tab → player A again, group modal open on MEMBERS with the loaded pages kept. Test: Task 7 Playwright `back restores group members tab`.
5. 429 or timeout on a lazy feed → inline retry message in that tab only; the rest of the profile keeps working. Test: Task 6 Playwright `feed 429 shows retry`.
6. A player leaves a group and their profile is reopened → the old group no longer counts as shared, while member-page edges from other groups stay. Test: Task 10 `profile snapshot replaces only profile edges`.
7. IndexedDB unavailable (private window, blocked storage) → exploring works; the connections section shows "Network unavailable in this browser". Test: Task 11 Playwright `network degrades without indexedDB`.

**Files:**

**Interfaces:**
- Produces (`playerNetwork.ts`):
  - `type NetPlayer = { id: number; name: string; displayName?: string; headshotUrl?: string | null }`
  - `type NetGroup = { id: number; name: string; iconUrl?: string | null; memberCount?: number }`
  - `type Membership = { userId: number; groupId: number; roleName?: string; roleRank?: number; source: 'profile' | 'members'; seenAt: string }`
  - `type NetworkState = { version: 1; players: Record<number, NetPlayer>; groups: Record<number, NetGroup>; edges: Record<string, Membership> }` (edge key `${userId}:${groupId}`; a `profile` edge wins over `members` for the same key)
  - `emptyNetwork(): NetworkState`
  - `recordProfile(s, player: NetPlayer, groups: (NetGroup & { roleName?: string; roleRank?: number })[], now: string): NetworkState`: replaces all `profile` edges of that player with this list; updates nodes.
  - `recordMembers(s, group: NetGroup, members: (NetPlayer & { roleName?: string; roleRank?: number })[], now: string): NetworkState`: adds or refreshes `members` edges only.
  - `sharedGroups(s, a: number, b: number): NetGroup[]` sorted by `memberCount` ascending (smaller groups are the more meaningful link).
